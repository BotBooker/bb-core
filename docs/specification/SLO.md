# SLO: цели по надёжности bb-core

| Поле | Значение |
| --- | --- |
| Версия | 0.1 |
| Статус | Draft |
| Область | `bb-core`: HTTP `:8080`, gRPC `:50051`, PostgreSQL |
| Связанные документы | [SLI.md](SLI.md), [SLA.md](SLA.md), [план внедрения](../plans/reliability-gaps-2026-10-30.md) |
| Последнее обновление | 2026-10-30 |

Документ задаёт **внутренние цели** по индикаторам из [SLI.md](SLI.md).
Внешние обязательства и последствия их нарушения — в [SLA.md](SLA.md).

RFC-ключевые: MUST — обязательно, SHOULD — рекомендуется, MAY — допустимо.

## 1. Принципы

- SLO — инженерная цель, а не юридическое обещание. Она строже SLA: запас
  нужен, чтобы внешнее обязательство не нарушалось из-за обычных колебаний.
- SLO считается по метрикам, а не по трассам и не по выборке логов.
- Окно SLO — **скользящие 28 дней**, шаг вычисления — 5 минут. Скользящее окно
  не обнуляется первого числа и не позволяет «переждать» плохой месяц.
- SLO действует **включая плановые работы**. Их исключение — привилегия SLA,
  а не внутренней цели.
- У каждого SLO есть бюджет ошибок, владелец и правило действий при его
  исчерпании (§5).
- Если SLI неизмерим, SLO не вводится: сначала устраняется блокер, потом
  фиксируется цель. Исключение — latency SLO, зафиксированный с явной пометкой
  блокера G1 по решению от 2026-10-30.

## 2. Окно, расчёт и бюджеты

Бюджет ошибок:

```text
error_budget = 1 - SLO
budget_time  = window × error_budget
burn_rate    = error_rate / error_budget
```

`burn_rate = 1` означает, что бюджет будет исчерпан ровно к концу окна.
`burn_rate = 14.4` за 1 час съедает 2 % 28-дневного бюджета.

| Цель | Бюджет за 28 дней | Бюджет за 30 дней |
| --- | --- | --- |
| 99,9 % | 40 мин 19 с | 43 мин 12 с |
| 99,5 % | 3 ч 21 мин 36 с | 3 ч 36 мин |
| 99,0 % | 6 ч 43 мин 12 с | 7 ч 12 мин |

Правила округления и данных:

- отношение считается по суммам `rate(...[5m])`, а не по средним значениям
  готовых отношений;
- при пропуске данных окно помечается `no_data` и разбирается; молча
  выбрасывать его нельзя;
- при объёме меньше 1000 бизнес-запросов за 28 дней доступность оценивается
  по SLI-9/готовности (см. [SLI.md](SLI.md), §5);
- плановые работы входят в SLO; аварийные — тоже.

## 3. Цели

| ID | SLI | Цель | Окно | Бюджет | Источник цели | Статус |
| --- | --- | --- | --- | --- | --- | --- |
| SLO-1 | SLI-1, доступность HTTP | 99,9 % | 28 дней | 40 мин 19 с | `technical.md` (99,5 %) + решение от 2026-10-30 | ✅ |
| SLO-2 | SLI-2, доступность gRPC | 99,9 % | 28 дней | 40 мин 19 с | то же | ✅ |
| SLO-3 | SLI-6, публичный каталог | 99,9 % | 28 дней | 40 мин 19 с | критический путь клиента | ✅ |
| SLO-4 | SLI-3, latency чтения | p95 ≤ 300 мс | 28 дней | 5 % запросов | `architecture.md` | 🚧 G1 |
| SLO-5 | SLI-3, latency auth | p95 ≤ 750 мс | 28 дней | 5 % запросов | Argon2id, решение от 2026-10-30 | 🚧 G1 |
| SLO-6 | SLI-5, готовность/БД | 99,9 % | 28 дней | 40 мин 19 с | `technical.md` | ✅ (грубо) |
| SLO-7 | SLI-7, сатурация | guardrails | 28 дней | нет | ёмкость и опыт эксплуатации | 🚧 |
| SLO-8 | SLI-8, долговечность | RPO 4 ч, RTO 4 ч, 100 % бэкапов | месяц | нет | решение от 2026-10-30 | 🚧 G3 |
| SLO-9 | SLI-9, ключевые сценарии | 99,9 % | 28 дней | 40 мин 19 с | внешняя проверка | ⬜ G8 |

ID SLO и SLI независимы: SLO-3 опирается на SLI-6, а SLO-4/SLO-5 — на SLI-3;
соответствие всегда указано в колонке SLI. Нумерация SLO не меняется при
добавлении новых SLI.

### 3.1. SLO-1 и SLO-2. Доступность

Цель 99,9 % — это не «красивая цифра», а запас над внешним SLA 99,5 %.
Разница в 0,4 п.п. — примерно 2 ч 53 мин в месяц, которые покрывают
обновления, краткие сбои БД и восстановление после инцидентов без нарушения
обязательства.

Доступность 99,9 % достижима только при выполнении предусловий HA из
[SLA.md](SLA.md): одна реплика и одна БД не дают такой гарантии. Пока HA нет,
SLO-1/2 остаются целями, а не обещаниями; их фактическое выполнение
отслеживается, но SLA не подписывается.

### 3.2. SLO-3. Публичный каталог

Публичный каталог — анонимная точка входа. Он выделен в отдельный SLO, потому
что общая доступность может оставаться высокой, пока ломается именно путь
`/api/v1/public/*` или `/t/{slug}`. Цель та же — 99,9 %, бюджет отдельный:
деградация каталога не должна «прятаться» в общем бюджете.

### 3.3. SLO-4. Latency чтения

Цель — p95 ≤ 300 мс по запросам группы read (см. [SLI.md](SLI.md), §4.3).
Это соответствует требованию `architecture.md` и проверяется как доля
запросов с `le="0.3"`: p95 ≤ 300 мс эквивалентно тому, что не менее 95 %
запросов укладываются в 300 мс.

**Блокер G1:** без явных границ гистограммы бакета `0.3` не существует.
До мержа фикса цель остаётся в документе, но дашборд и алерт помечаются
«не измеримо». Снижать цель до 5 с нельзя: это закрепит неверное поведение.

### 3.4. SLO-5. Latency auth

Argon2id с параметрами `m=19456, t=2, p=1` намеренно медленный: одна проверка
пароля — это десятки миллисекунд CPU и 19 MiB памяти. При лимите 1 CPU и
всплеске входов auth-ручки не могут гарантировать 300 мс. Поэтому отдельная
цель p95 ≤ 750 мс для `POST /auth/register`, `/auth/login`, `/auth/password`.

Отдельный SLO также защищает SLO-4: медленный login не тянет вниз latency
чтения и наоборот. Если появятся данные, что 750 мс избыточны, цель можно
ужесточить — но только после трёх месяцев наблюдений.

### 3.5. SLO-6. Готовность и доступность БД

Цель 99,9 % по ответам `/ready` = 200. Это грубая, но полезная проверка:
она ловит недоступность БД и ошибки `PingContext`. Ограничение — полный отказ
процесса: при отсутствии ответов серии нет, поэтому SLO-6 MUST
рассматриваться вместе с SLO-9 и состоянием реплик.

### 3.6. SLO-7. Сатурация

Это guardrails, а не SLO с бюджетом:

| Показатель | Порог | Действие |
| --- | --- | --- |
| Утилизация пула | < 80 % для 99 % 5-минутных окон | предупреждение, разбор запросов |
| Пустые acquire | > 0 в течение 10 минут | warning, проверить пул и БД |
| Среднее ожидание | < 10 мс | warning |
| CPU контейнера | < 80 % limit для 99 % окон | warning, проверить нагрузку |
| Память | < 85 % limit | warning, риск OOM/Argon2 |

### 3.7. SLO-8. Долговечность

- 100 % запланированных бэкапов успешны за календарный месяц;
- RPO ≤ 4 ч: максимальный интервал между успешными копиями;
- RTO ≤ 4 ч: восстановление на отдельной базе;
- restore-учение — не реже раза в квартал, результат в [RUNBOOK.md](../RUNBOOK.md).

**Блокер G3:** RUNBOOK уже требует бэкап каждые 4 часа, но автоматизации и
алерта нет, поэтому фактический RPO может быть больше. Пока G3 не закрыт,
SLO-8 — целевое требование, а SLA на RPO/RTO не подписывается.

### 3.8. SLO-9. Ключевые сценарии

99,9 % успешных внешних проб по SLI-9. Пробы должны работать из ≥ 2 локаций,
чтобы отличить отказ сервиса от сети одной точки. SLO-9 — единственный
источник, который видит полный отказ; до его появления доступность считается
только по серверным метрикам с оговоркой из [SLI.md](SLI.md), §5.

Владелец целей — backend-команда; эксплуатационные SLO-6…SLO-9 и алерты ведёт
SRE/эксплуатация. Владелец подтверждает бюджет и действия по §4.

## 4. Политика бюджета ошибок

Бюджет — не отчёт, а инструмент управления релизами. Правила действуют для
SLO-1, SLO-2, SLO-3, SLO-4, SLO-5 и SLO-9.

| Израсходовано бюджета | Что делаем |
| --- | --- |
| < 50 % | обычный режим; наблюдаем за burn rate |
| 50–75 % | разбор на недельной встрече; заморозка рискованных экспериментов; приоритет надёжности |
| 75–100 % | заморозка некритичных релизов; разбор инцидента; исключения — только с письменным согласием владельца |
| 100 % | полная заморозка некритичных изменений до восстановления бюджета; постмортем; пересмотр планов |

Дополнительные правила:

- один инцидент, съевший больше 20 % бюджета, требует постмортема независимо
  от того, исчерпан бюджет или нет;
- исправления безопасности и инцидентов выпускаются всегда, даже при
  исчерпанном бюджете;
- бюджет нельзя «сбросить» вручную: он восстанавливается только за счёт окна;
- если бюджет стабильно остаётся выше 50 % к концу окна, цель пересматривается
  в сторону ужесточения (или появляется новый SLO).

## 5. Алерты

Алерты строятся на burn rate, а не на одиночных ошибках: один всплеск 5xx не
должен будить дежурного, а устойчивое выгорание бюджета — должен.

| Алерт | Условие (28-дневное окно) | Severity | Действие |
| --- | --- | --- | --- |
| Fast burn | `burn_rate1h > 14.4` и `burn_rate5m > 14.4` | page | тушить инцидент, смотреть трассы и 5xx |
| Medium burn | `burn_rate6h > 6` и `burn_rate30m > 6` | page | разбор, проверка зависимости |
| Slow burn | `burn_rate3d > 1` и `burn_rate6h > 1` | ticket | плановый разбор, поиск системной причины |
| Readiness | доля `/ready` = 200 < 99 % за 5 минут | page | проверить БД, пул, логи |
| Latency read | доля ≤ 300 мс < 95 % за 30 минут | ticket | проверить пул, БД, маршруты |
| Latency auth | доля ≤ 750 мс < 95 % за 30 минут | ticket | проверить CPU, Argon2, очередь |
| Saturation | пул > 80 % за 10 минут | warning | проверить запросы и лимиты |
| SLA projection | прогноз доступности за месяц < 99,5 % | page | эскалация владельцу SLA |

Точные пороги `burn_rate` для 28-дневного окна: 14,4× за 1 час — примерно
2 % бюджета; 6× за 6 часов — примерно 5 %; 1× за 3 дня — примерно 10,7 %.

Алерты MUST ссылаться на runbook-раздел и содержать метку `slo` (ID цели),
чтобы дежурный сразу понимал, что горит. Правила и дашборды пока не лежат в
репозитории — это задача G7.

## 6. Отчётность и пересмотр

Ежемесячный отчёт (до 5-го рабочего дня):

- фактическое выполнение каждого SLO за скользящие 28 дней и за календарный
  месяц;
- остаток бюджета и динамика burn rate;
- инциденты, повлиявшие на бюджет, со ссылками на постмортемы;
- топ-5 маршрутов по вкладу в ошибки и latency;
- решения: что заморожено, что ускорено, какие цели пересматриваются.

Пересмотр целей — ежеквартально или после крупного инцидента. Изменение SLO
оформляется отдельным изменением документа и не действует задним числом:
нельзя «поднять» цель после того, как бюджет уже сгорел.

## 7. Исключения и особые случаи

- **Плановые работы** входят в SLO. В SLA они исключены, если анонсированы
  заранее ([SLA.md](SLA.md)).
- **Beta- и новые ручки** не входят в SLO первые 30 дней после включения.
- **Малый объём трафика** — порог 1000 бизнес-запросов за 28 дней; ниже
  используется SLI-9/готовность, иначе отношение недостоверно.
- **Пропуски данных** не выбрасываются молча: окно помечается `no_data` и
  разбирается. Для SLA пропуск считается недоступностью.
- **Полный отказ** серверными метриками не виден; SLO-1/2/6 MUST
  интерпретироваться вместе с SLO-9.

## 8. Связь с SLA

| Параметр | SLO | SLA |
| --- | --- | --- |
| Доступность HTTP | 99,9 % / 28 дней | 99,5 % / календарный месяц |
| Доступность gRPC | 99,9 % / 28 дней | 99,5 % / календарный месяц |
| Latency | p95 ≤ 300/750 мс | не входит в v1 |
| RPO/RTO | 4 ч / 4 ч | 4 ч / 4 ч после закрытия G3 |
| Плановые работы | входят | исключены при анонсе |
| Последствия | заморозка релизов | кредиты — в отдельном юридическом документе |

SLA не может быть строже SLO: если SLO не выполняется, внешнее обещание
держится только за счёт запаса. Поэтому SLA подписывается после трёх месяцев
наблюдений и выполнения предусловий из [SLA.md](SLA.md).

## Приложение A. Recording rules и алерты

Эскиз правил; перед применением MUST быть проверен `promtool check rules` и
сверен с фактическими именами метрик (G11). Фильтры маршрутов — как в
[SLI.md](SLI.md), приложение A; ниже они сокращены комментарием.

```yaml
groups:
  - name: bb-core-slo
    interval: 30s
    rules:
      # Доля хороших запросов; фильтры — как в SLI-1/SLI-3.
      - record: slo:sli_http_availability:ratio_rate5m
        expr: |
          sum(rate(http_server_request_duration_seconds_count{
            service_name="bb-core",
            http_route!~"/health|/ready|/api/swagger/.*|unmatched",
            http_response_status_code!~"5.."}[5m]))
          /
          sum(rate(http_server_request_duration_seconds_count{
            service_name="bb-core",
            http_route!~"/health|/ready|/api/swagger/.*|unmatched"}[5m]))

      - record: slo:sli_http_availability:ratio_rate1h
        expr: |
          sum(rate(http_server_request_duration_seconds_count{
            service_name="bb-core",
            http_route!~"/health|/ready|/api/swagger/.*|unmatched",
            http_response_status_code!~"5.."}[1h]))
          /
          sum(rate(http_server_request_duration_seconds_count{
            service_name="bb-core",
            http_route!~"/health|/ready|/api/swagger/.*|unmatched"}[1h]))

      - record: slo:http_availability:burn_rate1h
        expr: |
          (1 - slo:sli_http_availability:ratio_rate1h) / (1 - 0.999)

      # Алерты: fast/medium/slow burn. Пороги — из §5.
      - alert: BbCoreAvailabilityFastBurn
        expr: slo:http_availability:burn_rate1h > 14.4
        for: 5m
        labels:
          severity: page
          slo: SLO-1
        annotations:
          summary: "bb-core: быстрый расход бюджета доступности"
          runbook_url: "https://github.com/BotBooker/bb-core/blob/main/docs/RUNBOOK.md"

      - alert: BbCoreReadinessDown
        expr: |
          sum(rate(http_server_request_duration_seconds_count{
            service_name="bb-core", http_route="/ready",
            http_response_status_code="200"}[5m]))
          /
          sum(rate(http_server_request_duration_seconds_count{
            service_name="bb-core", http_route="/ready"}[5m])) < 0.99
        for: 5m
        labels:
          severity: page
          slo: SLO-6
        annotations:
          summary: "bb-core: /ready не отвечает 200"
```

Для gRPC, latency и сатурации правила строятся по тем же принципам; полный
набор появится вместе с G7.

## Приложение B. Расчёт бюджета

Пример для SLO-1 (99,9 %, 28 дней):

```text
window       = 28 × 24 × 60 = 40320 минут
error_budget = 0.001
budget       = 40320 × 0.001 = 40.32 минуты ≈ 40 мин 19 с
```

Если за сутки доля ошибок 0,5 %:

```text
error_rate = 0.005
burn_rate  = 0.005 / 0.001 = 5
```

За сутки сгорит 5 × (1/28) ≈ 17,9 % бюджета — это уровень medium burn,
требующий разбора, но не полной заморозки.
