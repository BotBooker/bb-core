# ADR 0001. Мультитенантность, вход по ссылке и переключение тенантов

- **Статус:** Proposed
- **Дата:** 2026-10-18
- **Контекст:** `bb-core`, схема `tenants`/`tenant_members`/`roles`, JWT-сессии,
  публичный каталог объектов, бронирование и оплата.
- **Уточнение (2026-10-18):** внутри установки появились суперпользователь
  (создаёт bootstrap) и глобальные операторы, которых он назначает; отдельного
  control plane по-прежнему нет.

## 1. Контекст

Сервис поддерживает несколько тенантов (организаций) в одной установке. Роль —
атрибут членства в тенанте (`tenant_members.role_id`), а не профиля пользователя.
Сессия действует в рамках одного тенанта: `user_tokens.tenant_id NOT NULL`,
JWT содержит claim `tenant` и снимок роли.

Сейчас:

- при входе выбирается самое раннее активное членство
  (`ORDER BY joined_at ASC LIMIT 1`), выбора тенанта нет;
- регистрация и вход без членства создают личный тенант;
- `tenant.v1` сгенерирован, но не зарегистрирован в HTTP gateway и gRPC;
- endpoint переключения тенанта отсутствует;
- приостановка тенанта и удаление членства не отзывают уже выданные токены;
- публичное чтение и видимость клиентов для staff не описаны.

## 2. Проблема

Пользователь может состоять в нескольких тенантах, но сессия действует только в
одном. Без явного выбора тенанта нельзя:

- войти в организацию, в которую пользователя пригласили;
- переключиться между организациями;
- гарантировать, что staff видит только данные своего тенанта.

Дополнительно нужно определить публичный каталог, доступ staff к профилям
клиентов, идемпотентность броней и платежей и поведение при отзыве доступа.

## 3. Требования

- Пользователь попадает в тенант по ссылке; ссылка открывает публичный каталог
  тенанта без обязательной аутентификации.
- Публичная информация доступна клиенту для всех тенантов.
- `tenant_slug` обязателен в login, switch и change-password.
- Регистрация по ссылке создаёт клиентское членство в тенанте ссылки.
- Admin, operator и manager видят клиента только в своём тенанте и только если у
  клиента есть любая бронь в этом тенанте, включая отменённые.
- Одна сессия — один тенант; переключение явное и аудируемое.
- Удаление членства, смена роли и приостановка тенанта должны немедленно
  влиять на доступ.
- Бронь и оплата идемпотентны по `Idempotency-Key`.
- On-premise: сервис устанавливается на стороне клиента; глобального control
  plane, service accounts и квот нет. Внутри установки bootstrap создаёт
  суперпользователя, а суперпользователь назначает глобальных операторов:
  оба уровня администрируют все тенанты.

## 4. Модель поставки: PaaS и on-premise

PaaS (Platform as a Service) и on-premise — способы поставки одного и того же
сервиса. Multi-tenancy работает внутри одной установки; отдельного центрального
control plane нет.

Для on-premise важны:

- Dockerfile, compose и Helm;
- миграции при старте или отдельным шагом;
- backup/restore и проверка восстановления;
- runbooks и документация по конфигурации;
- health/readiness и наблюдаемость без обязательного внешнего коллектора.

## 5. Вход по ссылке

Ссылка имеет вид `https://app.example/t/{tenant_slug}` или
`https://app.example/?tenant={tenant_slug}`.

Публичная страница тенанта:

- публичный профиль тенанта (название, slug, описание, локация);
- публичный каталог объектов тенанта;
- доступна без токена и без членства.

Публичный каталог всех тенантов остаётся доступным; ссылка задаёт tenant context
для брони и оплаты. Приватные ручки обязаны требовать tenant scope.

Регистрация по ссылке:

1. `POST /auth/register` с `tenant_slug`.
2. Тенант находится по slug и проверяется на статус `active`.
3. Создаётся пользователь и клиентское членство в этом тенанте.
4. Личный тенант при регистрации по ссылке не создаётся.
5. Ответ содержит `access_token`, `tenant_slug`, `tenant_id` и `role`.

Если email уже существует, регистрация возвращает `409`; пользователь входит
через login по ссылке. Если пользователь существует, но не является членом
тенанта, нужен отдельный `join` или приглашение.

## 6. Аутентификация и сессии

### Login

`POST /auth/login` принимает `email`, `password`, `tenant_slug`.

Сервер:

1. Находит тенант по slug (`TenantRepo.GetBySlug`).
2. Проверяет статус `active`.
3. Проверяет членство `(tenant_id, user_id)`.
4. Выдаёт JWT с tenant и ролью из членства.

Ошибки login не раскрывают существование пользователя или тенанта: используется
единый `401 invalid credentials`.

### Switch

`POST /auth/tenant/switch` принимает `tenant_slug`, требует действующий токен,
проверяет членство в целевом тенанте и выпускает новый JWT. Старый токен по
умолчанию не отзывается; для полного выхода есть `logout-all`.

### Logout

- `POST /auth/logout` отзывает текущую сессию.
- `POST /auth/logout-all` отзывает все сессии пользователя во всех тенантах.

### ChangePassword

`POST /auth/password` принимает `tenant_slug` и выдаёт новую сессию в указанном
тенанте. Это сохраняет текущее поведение «смена пароля сразу даёт доступ» и
согласуется с обязательным `tenant_slug`.

### Bootstrap

`cmd/bootstrap` создаёт первый тенант и администратора. Команда должна печатать
`tenant_slug` и готовую ссылку `/t/{slug}`; иначе первый администратор не сможет
войти при обязательном slug.

### Существующие личные тенанты

Новые регистрации по ссылке личные тенанты не создают. Существующие личные
тенанты не удаляются: они остаются legacy, администратор может узнать slug через
CLI или БД. Для пользователей без ссылки нужен способ узнать slug: админская
выгрузка, приглашение или отдельный lookup-сценарий.

## 7. Матрица доступа

| Актор | Публичный каталог всех тенантов | Данные своего тенанта | Клиенты своего тенанта | Клиенты других тенантов |
| --- | --- | --- | --- | --- |
| Аноним | read | нет | нет | нет |
| Superuser / Global operator | read | все тенанты | все клиенты | все клиенты |
| Client | read | свои брони, платежи и профиль | свой профиль | нет |
| Operator | read | по правам | только клиенты с любой бронью в тенанте | нет |
| Manager | read | по правам | только клиенты с любой бронью в тенанте | нет |
| Admin | read | по правам | только клиенты с любой бронью в тенанте | нет |

Предикат доступа staff к клиенту:

```sql
EXISTS (
  SELECT 1 FROM bookings b
  WHERE b.client_id = u.id
    AND b.tenant_id = :tenant_id
)
```

Фильтр по статусу брони не применяется: отменённые брони тоже дают доступ к
профилю клиента. Проверка выполняется в репозитории или сервисе, а не только в
транспорте. Глобального списка пользователей нет; `user.v1.List/Get` работают в
tenant scope. Исключение — суперпользователь и глобальные операторы: они
администрируют все тенанты, поэтому tenant scope для них не ограничение.

Staff видит коллег-участников своего тенанта через членство, но не видит
клиентов без брони в этом тенанте. Сценарий «staff создаёт первую бронь новому
клиенту» требует self-registration клиента или приглашения.

## 8. Публичная информация

Публично доступны:

- название, slug, описание и локация тенанта;
- объекты аренды, фото, описание, цена и дополнительные услуги;
- расписание и доступность слотов.

Не публикуются:

- PII клиентов;
- платежи и их статусы;
- уведомления;
- внутренние идентификаторы и служебные поля.

Suspended и deleted тенанты публично не показываются. Публичные ручки не требуют
членства; приватные ручки обязаны требовать tenant scope.

## 9. Бронирование и идемпотентность

`POST /bookings`:

- tenant берётся из токена;
- объект должен принадлежать этому тенанту;
- клиент — текущий пользователь;
- обязателен `Idempotency-Key`;
- уникальность: `(tenant_id, client_id, idempotency_key)`;
- повтор с тем же ключом возвращает ту же бронь;
- тот же ключ с другим payload возвращает `409`.

Тип бронирования (без ожидания, 1 минута, 30 минут, с подтверждением) требует
отдельной схемы: поля или таблицы с hold-политикой и фонового истечения
неподтверждённых броней.

## 10. Платежи и идемпотентность

`POST /payments`:

- tenant берётся из токена;
- `booking_id` принадлежит тенанту и клиенту;
- сумма берётся из брони; произвольный amount на первом этапе не принимается;
- обязателен `Idempotency-Key`;
- в `payments` добавляются `idempotency_key`, `external_id` и статус `pending`;
- уникальность: `(tenant_id, idempotency_key)`;
- повтор возвращает тот же платёж;
- тот же ключ с другой бронью или суммой возвращает `409`;
- вебхук провайдера идемпотентен по `external_id`;
- переходы: `pending → succeeded/failed/refunded`;
- успешный платёж обновляет статус брони и создаёт уведомление.

`Idempot_id` в требованиях трактуется как `Idempotency-Key`/`idempotency_key`.
Если это отдельное поле, в API добавляется alias, но в БД и контракте остаётся
одно имя.

## 11. Изоляция данных и миграция

В `rental_objects`, `bookings`, `payments` и `notifications` добавляется
`tenant_id`:

1. Колонка добавляется nullable.
2. Выполняется backfill: существующие строки привязываются к default/legacy
   тенанту.
3. Колонка становится `NOT NULL`.
4. Добавляются составные внешние ключи, не допускающие связей между тенантами:
   `(tenant_id, object_id)`, `(tenant_id, booking_id)` и аналогичные.
5. Уникальные ключи становятся tenant-scoped:
   `(tenant_id, client_id, idempotency_key)`,
   `(tenant_id, idempotency_key)`, `(tenant_id, dedup_key)`.
6. Индексы пересматриваются под выборки по `tenant_id`.
7. Миграция проверяется на PostgreSQL и SQLite, включая down и повторный up.

Ключи кэша, S3 и уведомлений включают `tenant_id`, иначе возможны cross-tenant
коллизии и утечки.

## 12. Отзыв сессий и статус тенанта

`Authenticate` проверяет:

- подпись и срок JWT;
- наличие и состояние сессии;
- пользователя;
- статус тенанта сессии (`active`);
- наличие членства и действующую роль.

Если членство удалено, снимок роли из токена больше не используется: запрос
отклоняется. При удалении членства, смене роли и приостановке тенанта сервис
отзывает затронутые сессии. `logout-all` отзывает все сессии пользователя.

Токен доступа живёт 30 дней по умолчанию, поэтому только проверка при login
недостаточна: статус тенанта и членство должны проверяться при каждом запросе
или сессии должны отзываться административным действием.

## 13. Рассмотренные варианты

| Критерий | JWT-switch | `X-Tenant-ID` | Re-login с `tenant_slug` |
| --- | --- | --- | --- |
| Совместимость с ERDB и claims | Высокая | Низкая: нужен пересмотр модели | Высокая |
| Отзыв и аудит | Явный, новый токен | Сложнее: один токен на все тенанты | Простой, но грубый |
| UX | Хороший | Хороший | Плохой: повторный ввод пароля |
| Сложность | Средняя | Высокая | Низкая |
| Риск cross-tenant | Низкий при проверке членства | Средний или высокий | Низкий |
| PaaS и on-premise | Подходит | Подходит, но дороже | Плохо для частых переключений |

## 14. Решение

1. Вход и переключение — через JWT-switch: `POST /auth/tenant/switch` с
   обязательным `tenant_slug`. Одна сессия действует в одном тенанте.
2. `tenant_slug` обязателен в login, switch и change-password. Неявный выбор
   самого раннего членства удаляется.
3. Регистрация по ссылке создаёт клиентское членство в тенанте ссылки; личный
   тенант при этом не создаётся.
4. Публичный каталог доступен без членства для всех тенантов; ссылка задаёт
   tenant context для брони и оплаты.
5. Staff видит клиента только при наличии любой брони в своём тенанте.
6. Бронь и оплата используют `Idempotency-Key`; платежи получают `pending`,
   `external_id` и tenant-scoped уникальность.
7. `logout-all` отзывает все сессии; административные изменения членства и
   статуса тенанта отзывают затронутые сессии.
8. PaaS и on-premise — модели поставки; глобального control plane, service
   accounts и квот нет. Внутри установки суперпользователь и назначенные им
   глобальные операторы администрируют все тенанты.

## 15. Последствия

Положительные:

- модель сессии остаётся совместимой с ERDB и JWT claims;
- пользователь может работать в нескольких тенантах без повторного пароля;
- staff получает предсказуемую область видимости клиентов;
- идемпотентность защищает от дублей броней и платежей.

Отрицательные и риски:

- login становится breaking change: клиенты обязаны передавать `tenant_slug`;
- существующие личные тенанты требуют политики миграции и коммуникации;
- при нескольких членствах пользователь должен знать slug или иметь ссылку;
- проверка статуса тенанта на каждом запросе добавляет обращение к БД или кэшу;
- публичный каталог требует отдельного allowlist и защиты от enumeration.

## 16. Тестирование

Unit-тесты:

- выбор тенанта по slug и проверка членства;
- обязательный `tenant_slug` в login, switch и change-password;
- регистрация по ссылке создаёт членство в тенанте ссылки;
- `logout-all` отзывает все сессии;
- visibility predicate для staff;
- идемпотентность брони и платежа: повтор и конфликт.

Интеграционные тесты:

- ссылка → публичный каталог → регистрация → бронь → оплата;
- пользователь тенанта A не видит приватные данные тенанта B;
- staff A видит клиента с бронью в A и не видит клиента без брони;
- staff A не видит клиента с бронью только в B;
- suspended/deleted tenant и удалённое членство;
- повторная оплата с тем же `Idempotency-Key`;
- вебхук с повторным `external_id`;
- миграция `tenant_id` на PostgreSQL и SQLite.

## 17. Открытые вопросы

1. `Idempot_id` — это `Idempotency-Key` или отдельное поле; нужно ли alias.
2. Существующие личные тенанты: оставить legacy или мигрировать в default tenant.
3. Публичный профиль тенанта: окончательный список публичных полей.
4. Полная матрица переходов статусов платежа и брони.
5. Пользователь существует, но не член тенанта: отдельный `join`, приглашение
   или автоматическое вступление по открытой ссылке.
6. Нужен ли invite-токен в ссылке для закрытых тенантов.
7. Staff видит коллег-участников тенанта; нужно ли отдельное правило для
   управления участниками.
